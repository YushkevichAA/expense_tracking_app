# Финансовый планировщик студента

Монорепозиторий MVP для планирования личного бюджета студента.

## Структура

- `backend/` — API на NestJS, TypeORM и PostgreSQL.
- `frontend/` — клиентское приложение на React и Vite.

## Быстрый старт

1. Установите зависимости: `npm install`.
2. Создайте файл окружения: `cp backend/.env.example backend/.env`.
3. Запустите PostgreSQL: `docker compose up -d postgres`.
4. Запустите клиент и API: `npm run dev`.

После запуска фронтенд доступен по адресу `http://localhost:5173`, API — по адресу `http://localhost:3000/api`, проверка состояния API — `GET /api/health`.

> В `backend/.env.example` `DB_SYNCHRONIZE=true` подходит только для локальной разработки. Перед развёртыванием необходимо использовать миграции TypeORM и установить `false`.

## Команды

- `npm run dev` — запуск API и клиента.
- `npm run build` — сборка всех приложений.
- `npm run lint` — проверка кода.
- `npm run test` — запуск тестов.

## Требования к MVP

1. Назначение приложения
   Приложение предназначено для планирования личного бюджета студента. Пользователь вручную вносит доходы, расходы и предстоящие платежи за обучение. Система рассчитывает баланс и помогает оценить, хватит ли средств на запланированные расходы.

В рамках проекта приложение не проводит платежи, не подключается к банковским счетам и не использует реальные данные студентов или университета. 2. Пользователи
Основной пользователь — студент, который ведёт учёт личных доходов и расходов.

Администратор для работы MVP не требуется: каждый пользователь управляет только своими данными. 3. Функциональные требования
ФТ-1. Регистрация и вход. Пользователь должен иметь возможность создать учётную запись и войти в приложение.

ФТ-2. Управление доходами. Пользователь может добавить, изменить и удалить запись о доходе. Для записи указываются сумма, дата, категория и необязательный комментарий.

ФТ-3. Управление расходами. Пользователь может добавлять, редактировать и удалять расходы. Для каждой записи указываются сумма, дата, категория и необязательный комментарий.

ФТ-4. Планирование платежей за обучение. Пользователь может указать сумму и дату планируемого платежа, например за семестр или курс. Платёж можно отметить как выполненный или оставить запланированным.

ФТ-5. Просмотр бюджета. Приложение показывает общую сумму доходов и расходов за выбранный период, текущий баланс и сумму предстоящих платежей.

ФТ-6. Фильтрация записей. Пользователь может просматривать доходы, расходы и платежи за выбранный период и по категории.

ФТ-7. Сводка. Система должна отображать краткую сводку по бюджету. Баланс за период рассчитывается по формуле:

Баланс = сумма доходов − сумма расходов.

Запланированные платежи показываются отдельно и не включаются в фактические расходы до тех пор, пока пользователь не отметит их как выполненные.

ФТ-8. Изоляция данных. Пользователь может просматривать и изменять только собственные записи.

ФТ-9. Проверка вводимых данных. Система должна проверять, что сумма указана числом больше нуля, а дата и обязательные поля заполнены. 4. Нефункциональные требования

- Удобство использования. Основные действия — добавление записи и просмотр сводки — должны быть доступны через понятный интерфейс.
- Адаптивность. Интерфейс должен корректно отображаться на компьютерах, планшетах и смартфонах.
- Производительность. При обычном объёме данных основные страницы и операции должны открываться без заметных задержек.
- Безопасность. Пароли пользователей должны храниться в защищённом виде. Доступ к данным должен предоставляться только после входа в систему.
- Надёжность расчётов. Итоговые суммы и баланс должны пересчитываться после добавления, изменения или удаления записи.
- Совместимость. Приложение должно работать в актуальных версиях распространённых браузеров.
- Защита данных. Для демонстрации следует использовать тестовые данные. Сбор банковских реквизитов, паролей от банков и иных избыточных сведений не предусматривается.
- Сопровождаемость. Программа должна иметь понятную структуру, чтобы её можно было дополнять новыми категориями и видами отчётов.

5. Ограничения проекта
   В MVP не входят проведение платежей, подключение к банкам, автоматическое получение операций по карте и интеграция с информационными системами университета. Все сведения о доходах, расходах и платежах пользователь вводит самостоятельно.
